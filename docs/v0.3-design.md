## 一、红队审查发现（v0.2 盲区，全部已取证）

### F1. 词表外漏网：「X 完成」结构不在 CLAIM 词表（真漏网）
- 现状：CLAIM 只认「已落地/已完成/已修好/…」等 10 个词，全是「已X」或「X好了」形态。
- 证据：audit-blindspots.mjs 超集探针，409 轮语料 → 28 轮现词表漏掉的有声明轮。
  人工复核真形态 3 例（session-91245193）：
  - turn 36「调研完成——三个顶级源全部到手」
  - turn 59「两个方向调研完成」「任务编排补充调研完成——两个新源到位」
  - （audit 另见「7 个全部接入完成」形态，来自其他会话）
- 附带发现：这些句子还含「调研」→ THIRD_PARTY 词表二次豁免 → 双保险放行。

### F2. 「先取证、后汇报」的轮次天然零工具 → 简单扩词表必误报（结构性矛盾）
- 证据（probe-window.mjs，session-91245193）：
  - turn 36：窗口内工具 = read/edit/pwsh/cordis_define/cordis_run/pwsh/cordis_undefine/mem_save_prompt（用户「可以了」之后），声明轮本身只有 1 次 pwsh（命令不含 VERIFY_CMD）。
  - turn 59：窗口内 mcp__github 调用 ×8 + read + pwsh，声明轮本身只有 pwsh ×2。
- 推论：把「调研完成」加进词表 + 保持单轮证据判定 → turn 36/59 必判 unverified（误报）。
  → **证据窗口必须从「本轮」放宽为「自最近真实用户消息以来」**（任务单元语义，
    与 SWE-bench 的"一个实例 = 一个任务单元"同构）。
- 边界风险：turn 8 真阳形态（零工具报「API 测试全部成功」）若其窗口内有其他任务的工具，
  窗口放行会漏掉它 → 需要专项测试 + 分级处理（见设计 D2）。

### F3. 召回方向无防线（结构性盲区）
- 证据：real-corpus.test.js 8 条用例 = 真阳 2 条 vs 误报防线 4+ 条；README 自认
  「⚠️ 召回率未知（真阳样本仅 2 条）」。
- 推论：判据体系单向朝「少误报」优化，没有一条测试防「该抓的没抓到」。
  v0.3 必须补 recall 矩阵（每条词表形态 + 每条窗口边界都有真阳测试）。

### F4. exit≠0 的失败验证算「已验证」（理论洞，语料无实害）
- 现状：decide 只看 tool/call 的 args 判 verified；tool/result 只做空跑撤销，
  从不看工具是否失败。「Select-String 找不到（exit 1）+ 声称已修复」→ ok。
- 证据：audit-blindspots B 探针 = 0 例同现（语料无害），但 measure-real-pain 证实
  pwsh 失败正文带 `[exit code: N]` 标记 → 防御性修复成本低（配对 callId 或正文标记）。

### F5. INLINE_EVIDENCE 先于 THIRD_PARTY/DENIAL 的顺序（理论洞，语料无实害）
- 证据：audit C 探针 31 例同现全部人工复核为合理放行（真验证+顺带他方词）。
- 结论：**不重排**。重排会把「子智能体 11/11 全绿」这类合理句误拦。记录为已知设计取舍。

### F6. 单会话事件数可达 124 万（旧 probe），decide 每轮全数组扫描
- 现状：95,525 事件最后一轮 2ms（审计 D 探针）→ 124 万约 26ms 线性外推，可接受不优化。
- 若未来变慢：窗口化 decide 本身就把扫描范围限制到窗口内，顺带解决。

### F7. 自检盲区（部分已修）
- 早期 probe 行已废弃；error 落盘已有。缺：decide 耗时未记（可加 ms 字段）、
  无定期重放审计（audit-blindspots.mjs 沉淀为常驻工具，README 加用法）。

## 三、v0.3 设计决策（草案，待外部视角交叉后定稿）

### D1. 词表结构化扩展（F1）
- 在「已X」之外补「X 完成」结构：有限动作词表 + 完成/完毕/收工/搞定。
  动作词候选（从真实语料提取，宁缺毋滥）：调研、接入、安装、部署、迁移、重构、
  落地、验证、修复、实施、导出、导入、备份、恢复、合并、提交、推送、拉取、扫描、
  审计、清理、删除、创建、生成、配置、升级、降级。
- 守卫（DENIAL 扩展）：未完成/尚未完成/待完成/还没完成/需要完成/要继续完成…
- 每条候选词必须过 409 轮语料对照：新增 unverified 数 = 0 或人工复核全真阳才保留。

### D2. 证据窗口（F2）
- 窗口 = 自最近一条真实用户消息（role=user 且 source.kind!=='plugin'）以来的事件区间。
- verdict 分级：
  - no-claim：无声明
  - ok：有声明，窗口内验证工具命中（reason: same-turn | window）
  - unverified：有声明，窗口内零验证（reason: missing）或空跑（vacuous）
- 声明检测仍限 data.turn===turn（只拦「这一轮说的话」）。
- 配置：windowMode 默认开；可回退旧单轮行为。
- 边界测试矩阵（recall 方向）：
  1. turn 8 形态：窗口真空 + 声明验收结果 → unverified
  2. turn 36 形态：窗口密集工具 + 「X 完成」 → ok（不误报）
  3. 窗口只有 todo_write/render_ui → unverified（黑名单在窗口内同样生效）
  4. 窗口跨多个用户请求 → 只算最近请求

### D3. 失败证据撤销（F4）
- tool/result 正文含 `[exit code: [1-9]\d*]` 或明确失败标记 → 该工具不计入验证。
- 实现：先收集失败标记（正文扫描），最终 verified 判定排除同轮/窗口内失败调用。
- 防御性（语料 0 实害），成本低，做。

### D4. 召回测试矩阵（F3）
- 新增 test/recall.test.js：每条词表形态一真阳 + 每条守卫一误报防线。
- audit-blindspots.mjs 沉淀常驻：README 写明「改词表/判据后必须跑 409 轮对照」。

### D5. decide 返回 evidence 摘要（auditHint 增强）
- 返回 evidence: string[]（本轮+窗口命中的验证工具名），steer 文本点名证据，
  缓解表演验证 + 帮 agent 自查「证据是否覆盖声明」。

## 五、实测定案（实现后新增发现，全部有语料证据）

### F9. 事件流乱序回流 → 窗口必须按 data.turn 归属，不能按位置（推翻 D2 草案实现）
- 证据（probe-turn-field.mjs，session-91245193 idx 4300-4360）：tool/result **延迟乱序回流**
  ——t=34/36/38/49 的 result 出现在 turn 51 区段中途（idx 4347/4351/4353/4355）；且真实用户消息
  出现在 turn/start(N) 之后、无 data.turn（4311 用户消息在 turn/start(51) 与 step/start(51) 之间）。
- 按「事件位置」找窗口起点会把 turn 36 的窗口起点错算到 turn 51 的用户消息 → 误拦 40 轮汇报。
- 定案：窗口起点 W = 最近一条「归属 turn ≤ 声明轮」的真实用户消息的归属 turn
  （归属 = 其前最近 turn/start 的 turn 号）；窗口 = { e : data.turn ∈ [W, turn] }。
  无真实用户消息（历史回放）→ 单轮语义（v0.2 兼容）。R3d 守住兼容。

### F10. pwsh 内容型取证被误判（turn 36 修复后的次生发现）
- 证据：turn 36 窗口内唯一 pwsh = 下载抓取（anthropic frontend-design SKILL.md 等），
  result 17,761 字符真实内容——命令不含 VERIFY_CMD → v0.3 判 unverified（误报）。
- 定案：pwsh 非 VERIFY_CMD 调用记 pendingPwsh；其 result 成功且正文 ≥200 字符 →
  提升为证据（「pwsh:content」）。短输出（echo hi）不提升——防表演验证防线保留（R6b）。
- 呼应 SA2「拒空输出」防表演三件套。

### F11. markdown 列表状态行漏剥（第 4 种结构形态）
- 证据：session-91245193 turn 14 回答「哪些落地了」，命中句「- **v4 自主性放宽**（你后来的
  要求）：✅ 已落地」——v0.2 剥 UI JSON/表格/引号三种结构，列表状态行是漏网的第 4 种。
- 定案：行剥离要求「列表行 + 冒号 + 状态 emoji + 已/未短词结尾」，防误剥
  「- 结论：已修复并验证通过」这类正文列表声明（R7c）。

### F12. 空跑检测自指误报（v0.3 修复期现场抓到，三层修复）
- 证据：session-8d0d184b turn 4——claim-gate 拦截主 agent 的审计轮后，该轮窗口内
  read 了自己的源码 lib/index.js：SUITE_EMPTY 定义行/注释里的空跑摘要字面
  （`# pass 0`/`no tests ran`/`[no test files]`）被子串正则命中 → 假空跑 → 误拦整轮。
  批量调用流（多个 read/pwsh 连发）下 call→result 错配加剧；调试脚本打印触发词也命中。
- 定案（三层，各配回归测试 R8a-d）：
  1. 计数形态行首锚定（^\s*…\b；node:test/mocha/jest 空跑摘要都在行首）；
     `[no test files]` 是 go test 的行中形态（`ok pkg [no test files]`），保留子串但
     加负向断言排除转义形态 `\[…\]`（源码定义行不自指）；
  2. call→result 配对从「交替流 lastCallName」改为 FIFO 未决队列（宿主按调用序回 result，
     批量连发不再错配；乱序迟到 result（F9）残余为漏报方向，接受）；
  3. vacuous 只判「测试运行命令」（TEST_CMD：npm test / node --test / pytest / mocha /
     jest / vitest / go test）的输出——read/grep/调试命令的正文永远不可能是测试结果。
- 连带纪律：检测器源码注释不得写裸触发词（已清理）。
- 教训沉淀：lesson 库「自指检测」条目。

### F13. 失败撤销越权（独立审计 cbbcd744 定案，88/100 扣分项）
- 证据：审计代码审查发现——内容型 pwsh（非 VERIFY_CMD，call 时不入 evidence 栈）失败时，
  旧实现仍 pop「最近一条非 null evidence」，会误撤销同窗口内一次无关的真验证
  （Test-Path 成功 → 随后 curl 抓取失败 → Test-Path 证据被 pop → 真「已修复+已验证」
  误判 unverified，误报方向）。R4b 只覆盖 VERIFY 型 pwsh 失败，此组合无测试。
- 定案：pending 队列元素记录自己的证据槽位（evIdx），失败只置空自己的槽
  （置 null 不 splice，索引稳定；输出端 filter(Boolean) 清理）。内容型失败不撤销任何东西。
- 回归：R4c（Test-Path 成功 + curl 失败 → ok）；60/60 全绿；四定案点与语料门禁 0 回归。

## 六、外部对标结论（三个子代理，全部带回核实源）

### SA1. cc-safety-net（1,518⭐）——机制错配澄清
- **不是**「轮末声明-证据闸门」，是 **PreToolUse 预执行命令闸门**（静态零 LLM 解析命令，
  命中规则书就 deny）。README 若把它当同机制引用属错配——本仓 README 只引它的哲学原话与
  「先看误报率再开 enforce」方法论，**无机制错配**，无需改。
- 可搬实践：ruleId 稳定文案（命中+为什么+替代动作）；三态 allow/deny/ask（拿不准提示而非硬堵）
  → 对应本仓 unverified(拦)/ok(软提示) 两档 + fail-safe；allow 白名单/override/分档 = 配置侧；
  fail-closed 契约「throw 则不得执行」→ 本仓反向（fail-safe：catch 静默放过）是有意取舍；
  **issue #41 实锤字符串误伤**（元话语/引述「rm -rf /tmp」被拦）→ 本仓引号剥离是同一防线的先例；
  残余风险登记（residual-risk.md RR-1..9 + 裁决日期）→ 本仓已知取舍段同理。
- 警示金句（config-recovery.md）：「判据可被 agent 反制时，『异常即拦截』是伪安全，只会锁死用户」。
  本仓 enforce 下拿不到验证数据的轮次 steer 要慎（turn 27 定案同此理）。

### SA2. AI control / spec-gaming / 验证器文献（15 条 URL 全部核实）
- Top3 落地映射：⑤ 双通道分离（只信 tool/result 结构事实不信散文）→ 本仓 F8（v0.2 读
  不存在的 data.result，v0.3 改读 message.content 嵌套正文）；② 成败判定（exit 0+正向信号）→
  本仓 F4 失败撤销 + F10 内容确认；④ 防表演验证（拒空输出/反重放/特异性）→ 本仓 vacuous 空跑
  检测 + pwsh:content ≥200 阈值 + evidence 点名。
- Goodhart 警示（2503.11926：检测器会被混淆化/Goodhart）→ 任何 LLM 判据加入前先问
  「agent 能否通过换措辞/加噪声绕过」，正则判据的对抗韧性靠结构事实不靠措辞。

### SA3. Claude Code hooks 生态（官方文档原文核实）
- 官方三级模式：command hook（确定性正则，本仓现状）→ prompt hook（单轮 LLM）→ agent hook
  （带工具子代理，experimental）。**本仓定位 = command hook 层**，升级路径已明确但不做：
  turn-stopping 是 serial，绝不在此发 LLM/子代理（README 设计取舍）。
- 社区同构两家：dmitry block_false_completion@Stop、oloapozram stop-verify@Stop
  （跑真实校验器红了才 block）——「拦截消息写可执行下一步」本仓 steer 已具备；
  fail-open/熔断（宿主 8 连拦强制放行）→ 本仓 fired 防同轮死循环 + fail-safe，会话级连拦
  熔断未做（低频场景，记录）。
- 挂载点扩展候选：SubagentStop/TaskCompleted 等价物（DSH 侧子代理完成事件）——需宿主事件
  支持，超出 v0.3 范围，记录为 future。
- 干预消息 9 条清单：reason 必填 + 「为何要继续」语义、一句话一个动作、≤10,000 字符 →
  本仓 steer 文案已对齐（短、具体、指向下一步）。
